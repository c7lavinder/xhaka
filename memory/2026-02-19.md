### Why V1 Failed (Full Post-Mortem)
1. Features before foundations
2. Monolithic architecture — one thing breaks, everything suspect
3. Hardcoded for NAH — couldn't replicate without touching code
4. DRY_RUN as only safety net — all or nothing, no nuance
5. Polling as primary trigger — race conditions, false triggers
6. No observability — Railway logs only, no audit trail
7. Silent failures — agents failed mid-execution with no recovery
8. Nothing testable in isolation
9. No human trust layer — team had no visibility
10. Kept shipping before stabilizing
11. No scope enforcement — buyers got seller workflows, nothing structurally prevented it

### Core Architecture Decisions Made Today

**The Org Chart (4 layers)**
```
Managers → Supervisors → Sub-Agents → [Bot Toolbox off to side]
```

**5 Departments**
- Lead Gen Manager (coming soon)
- Acquisitions Manager → 3 supervisors: New Lead Process, Acquisitions, Follow Up
- Dispo Manager → 6 supervisors: Deal Packaging, Buyer Lead Gen, Property Showings, Buyer Organization, Buyer Offers, TC Work
- Ops Manager → 2 supervisors: Data, Reporting
- Finance Manager (coming soon)

**Bot Layer**
- Bots execute only, zero decisions
- Fed by 3 separate concerns:
  - WHAT: Industry Agent (wholesale-specific knowledge)
  - HOW: CRM Agent (GHL-specific knowledge)
  - WHEN: Rulebook (business rules)

**Intelligence Services Layer** (agents call these, they don't execute)
- Call: Disposition, Summary, Next Step, Objection Identifier, Quality Scorer, Sentiment
- Lead: Scorer, Motivation, Price Gap, Dead Detector, Re-engagement
- Communication: Message Crafter, Response Interpreter, Objection Handler, Tone Matcher
- Deal: ARV Estimator, Repair Estimator, Offer Calculator, Deal Scorer
- Business: KPI Extractor, Trend Analyzer, Risk Assessor

**CRM Adapter Pattern**
- Core never talks directly to GHL
- Standard interface, multiple adapters (GHL today, HubSpot/Salesforce future)

**Agent Scope Enforcement**
- Every agent has a defined scope: pipeline, stages, contact type
- CRM adapter filters before agent sees any contacts
- Rulebook eligibility check before every action
- Scope is config-driven, auditable, changeable without deployment

**The Rulebook**
- Central policy engine
- Per-bot hours (SMS 8am-8pm, Email 8am-9pm, etc.)
- Suppression rules, rate limits, kill switches
- Editable from Control Room, no code change needed
- Every audit log entry captures which rule governed it

**Intelligence Layers (for "what to say")**
1. Platform Intelligence — aggregate across all tenants (the moat)
2. Industry Playbook — curated best practices
3. Tenant Context — this specific business

**5 Foundations (build first)**
1. Config System (per-tenant, auto-built by setup wizard)
2. Audit Log (every action recorded with full context)
3. Rulebook (central policy engine)
4. Bot Layer (atomic, reliable, logged)
5. GHL Integration Layer (clean CRM adapter)

**Human Involvement**
- 95%+ confidence → execute silently
- 75-95% → execute, flag for passive review
- Below 75% → one-tap approval card for human
- Never surface technical errors to humans
- Target: handful of one-tap moments per week across whole business

**The Confidence Engine**
- Every action has a confidence score
- Graduated response — not all-or-nothing like v1's DRY_RUN
- System self-heals where possible

### Additional Architecture Decisions

**Build Order**
- Backend FIRST — engine, database, agents, APIs only
- In ~2 weeks, use Manus to build Gunner UI on top of clean APIs
- Desktop first, mobile very important (NOT mobile-first — corrected)
- OpenAPI/Swagger spec maintained so Manus knows what's available

**Playbook — Full Contents Defined**
- Industry identity (terminology, tone, pain points)
- Process definitions (SLA per stage, stage meanings, escalation triggers)
- Scoring weights (factors, thresholds, urgency signals)
- Intelligence service defaults (prompt templates, model tiers — NOT exposed to tenants)
- Communication defaults (tone by stage, time-of-day guidance)
- Rulebook defaults (hours per bot, rate limits — platform decides, NOT tenants)
- Format: JSON file in repo for now, versioned

**Tenant Overrides — Minimal by Design**
- Goal: 90% of tenants complete 4-step wizard, never touch a setting again
- Tenants provide: business name/market, team members/roles, packages, pipeline mapping
- Tenants do NOT configure: when to send, what to say, scoring weights, escalation thresholds
- Platform makes those decisions — data refines over time
- Less configuration = higher floor for everyone

**Setup Wizard — Confirmed Design**
- Lives in Gunner
- Form-based: multiple choice + mapping ONLY (no text entry, no custom words)
- Step 1: Connect CRM (OAuth)
- Step 2: Auto-discover pipelines/stages/team
- Step 3: Pipeline mapping (dropdown + drag-and-drop)
- Step 4: Team roles (assign from discovered users)
- Step 5: Activate packages (toggle cards)
- Step 6: Review Rulebook defaults (pre-filled, rarely changed)

**After-Hours — Final Definition**
- Some bots run 24/7: Task Bot, Note Bot, Pipeline Bot (internal, no external impact)
- Some bots restricted: SMS Bot (e.g. 8am-8pm CST), Email Bot (8am-9pm)
- Time of day also influences WORDING — Message Crafter receives time of day as context
- Morning vs evening vs late = different tone in messages
- All in Rulebook, per-bot configurable

**Gunner — Role-Based Pages**
- Different pages per manager based on responsibility
- Acquisitions Manager = most pages (most built)
- Each manager section expands as functionality is built
- Team members see only their department's view (scope-enforced)

**V1 Failure #11 — Agent Scope Enforcement**
- Agents had instructions about who to act on but nothing STRUCTURALLY preventing wrong contacts
- Buyers got seller workflows in v1
- V2 fix: CRM adapter filters by scope before agent sees ANY contacts
- Three layers: Structural scope (fence) + Rulebook eligibility (gate) + Intelligence context (brain)
- Scope defined in config, not code — auditable, changeable without deployment

**Additional Gaps Addressed**
- Idempotency: fingerprint = tenant+contact+action+window, stored in executed_actions table
  - SMS: 24h window, Task: 1h, Pipeline move: immediate dedup, Note: no window
- Returning leads: is_returning_lead flag permanent, modified intake (skip intro, use history)
- Learning loop: message+response pairs stored, human edits = training signal, outcomes tagged back
- Graceful degradation: retry with backoff → fallback mode (templates) → circuit breaker
- Webhook queue: GHL events → validate → queue → agents consume (prevents lost events + idempotency)
- Contact thread vs GHL: GHL = source of truth for CRM data, our DB = AI intelligence layer only
  - We store: motivation scores, agent action history, is_returning_lead, confidence history
  - We do NOT duplicate: name, phone, email, pipeline stage, tags, notes
